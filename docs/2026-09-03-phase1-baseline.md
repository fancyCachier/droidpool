# Phase 1 性能基线与并发上限（2026-09-03）

> 节点 .54（Orange Pi 5B / RK3588S 8 核 / 16 GB / 116 GB eMMC）· 镜像 `redroid/redroid:14.0.0_64only-latest`
> profile `1366×768 @ 160 dpi`（= 收银机实机 Sunmi D1s 2nd 实测）· `androidboot.use_memfd=true` · GPU guest（SwiftShader 软渲染）
> 被测对象：cashier-app debug arm64，`login_flow` = 冷启动 → 隐私政策 → 设备角色 → 选员工 → PIN×6 → 登录 → 关 OTA 弹窗 → 桌台首页

### 2.1 三个结构性发现

**CPU 在 N=4 就封顶，之后靠排队消化。** 峰值 total_cpu 从 N=4 起稳定在 900 % 附近不再上涨，8 核已跑满。N=8 时 load 达到 44、N=12 时达到 76，但流程仍能跑完，说明积压主要是调度与 IO 等待，不是纯算力枯竭。代价体现为时延而非失败。

**真正的拐点是 swap，不是 CPU 也不是温度。** N=10 时 swap 为零、30 个样本零失败、中位 1.51× 与 p95 1.57× 几乎重合（无长尾）；N=12 时 swap 590 MiB，立刻出现 2 个超时失败，分布从紧凑变成长尾（中位 1.77× 但 p95 2.66×）。eMMC 随机读写只有 3300 IOPS，一旦换页介入，时延非线性恶化。**只看均值会完全漏掉这个拐点**——N=12 的均值 1.77× 仍在判据线内。

**冷启动是对并发最敏感的指标。** 4.3 s → 10.1 s（2.3×），而整体流程只到 1.51×。并发主要惩罚启动阶段，登录后的点击与 dump 受影响小。池子若要提高吞吐，优先避免多台设备同时冷启动。

### 2.2 内存是唯一线性且无饱和的资源

| N | 峰值 mem_used | 每容器增量 |
|---|---|---|
| 1 | 2199 MiB | 约 1150 MiB |
| 8 | 10048 MiB | 约 1125 MiB |
| 10 | 11474 MiB | 约 1042 MiB |
| 12 | 12350 MiB | 约 942 MiB |

每容器增量从 N=10 起下滑，不是节省，是内核开始回收与换页。宿主基线约 1050 MiB，15.6 GB 可用总量对应硬上限约 13 台。

## 3. 容器本身几乎不耗 CPU

8 个容器在 app `force-stop` 后静置采样：**total_cpu 合计 1 %、mem_used 6975 MiB**（每台约 740 MiB）。

即 redroid 容器的常驻开销几乎全是内存，CPU 开销全部来自 app 前台渲染（软渲染下每次重绘都是 CPU）。这条直接决定池子的设计：**租约空闲时 `force-stop` app，一台设备的常驻成本就只剩约 740 MiB 内存**，比 app 运行时的 1125 MiB 少三成，且不占 CPU。

## 5. 对 Phase 2 的输入

- **`max_devices = 8`**（配置默认值）。实测活跃上限是 10，取 8 留一档余量给设备墙的截图循环与人工放大时的 scrcpy 软编码——这两项在 Phase 1 里没有一起加压。
- **租约空闲即 `force-stop` app**。常驻成本从 1125 MiB 降到 740 MiB，且释放全部 CPU。`droidpool` CLI 在 `release` 前、以及租约超过 N 分钟无 adb 活动时执行。
- **claim 时错开冷启动**。冷启动是 2.3× 的敏感项，`droidpoold` 应串行化 `am start`，避免多台同时冷启。
- **监控 swap 而不是 CPU 或温度**。swap > 0 是唯一有预警价值的信号，池子应在 swap 出现时拒绝新 claim。CPU 早在 N=4 就饱和，温度全程不超过 70 °C，两者都不是有效的准入指标。
- **`uiautomator dump` 2.6 s 是驱动瓶颈**，一个 login_flow 要十余次。CLI 应缓存 dump 结果按需刷新。
