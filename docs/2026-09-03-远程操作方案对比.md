# 远程操作的帧率与延迟：实测、同类方案对比、改进路线（2026-09-03）

> 起因：设备墙的放大操作视图人工用起来钝，点下去不知道有没有生效，会重复点造成误操作。
> 本文给出实测数字、与 scrcpy / ws-scrcpy / STF 的对比，以及分三档的改进路线。

## 1. 实测：现状有多钝

节点 .54（RK3588S），设备 redroid 14 @ 1366×768，控制面在本机 Mac，全程内网。

| 指标 | 实测 | 说明 |
|---|---|---|
| **点击到画面变化** | **中位 1122 ms** | 人的体感指标。修锁之前是 1491 ms |
| 输入注入（`/api/.../input`） | 中位 119 ms，最慢 321 ms | 修锁之前最慢 1701 ms |
| 画面帧率 | 3 fps | 上限由 `adb exec-out screencap -p` 决定 |
| 单帧 `screencap -p` | 330~460 ms | 设备侧全屏抓取 + PNG 编码 |
| 裸帧缓冲 `screencap`（无 -p） | 610~710 ms，4.2 MB | 更慢：省下的编码时间被传输吃掉 |
| 服务端转码（解 PNG + 编 JPEG） | 约 300 ms | 已通过「全分辨率直通 PNG」消除 |
| `adb shell` 空往返 | 70 ms | 输入的固定成本 |

**结论：1.1 秒的点击反馈是差的。** 人类可接受的直接操作反馈在 100 ms 量级，
超过 1 秒会明确感到「没反应」。

### 1.1 已经做掉的两处

| 改动 | 效果 |
|---|---|
| 全分辨率流直通 PNG，不再解码重编码 | 帧率 1.0 → 2.4 fps |
| adb 锁按设备拆分，且输入不再与抓图共用锁 | 输入最慢 1701 → 321 ms；点击到画面 1491 → 1122 ms |
| 帧去重（画面没变就不推） | 静止时节省节点 CPU 与带宽 |

### 1.2 剩下的 1.1 秒花在哪

```
输入注入        ~120 ms
设备渲染新画面  ~200 ms   （Flutter 在软件渲染下本身就慢）
等下一帧        ~350 ms   （帧间隔 330~460 ms，平均等半个周期，最坏等满）
解码 + 绘制      ~30 ms
观察到「稳定的新画面」还要再等 1~2 帧（过渡动画）
```

瓶颈是**每帧 350 ms 的 `screencap`**。它是设备侧全屏抓取加 PNG 编码，
在软件渲染的 redroid 上尤其贵。这条路已经榨干了。

## 2. 对照：scrcpy 在同一台设备上能到多少

同一台 redroid，录制 8 秒：

| 方案 | 帧率 | 编码 |
|---|---|---|
| 本项目（screencap + MJPEG） | 3 fps | PNG，逐帧全屏抓 |
| **scrcpy 4.1** | **10.4 fps** | H.264，82 帧 / 8 秒 |

**scrcpy 快 3.5 倍**，而且这 10 fps 就是该设备软件渲染的实际出帧能力
（redroid 无硬件编码器），也就是说 scrcpy 已经贴到设备天花板，而我离天花板还差 3.5 倍。

## 3. 同类项目怎么做的

### scrcpy（Genymobile）

- 往设备推一个 `scrcpy-server.jar`，用 `SurfaceEncoder` + Android `MediaCodec`
  把显示内容直接编码成 H.264/H.265，**不经过 PNG，不逐帧往返**。
- **只在画面变化时产生帧**，静止时不出帧（用 `KEY_REPEAT_PREVIOUS_FRAME_AFTER` 定期补关键帧防花）。
- 视频、音频、控制**各走一条持久 socket**。
- 输入用隐藏 API `InputManager.injectInputEvent()` 注入，**不 fork `adb shell input`**。
- 客户端拿到帧立刻显示，默认零缓冲。

### ws-scrcpy（NetrisTV）

浏览器版 scrcpy。用改造过的 scrcpy 服务端，H.264 经 WebSocket 送到浏览器，
四种解码器可选：**WebCodecs**（浏览器内建解码器，最优）、MSE、Broadway（wasm）、TinyH264（wasm）。
支持多点触控、键盘、剪贴板双向、拖拽推文件、远程 shell。

服务端要 Node.js v10+ 与 node-gyp，`adb` 需在 PATH。

已知问题：模拟器上服务端监听在内部网卡；TinyH264 有时起不来；MSE 丢帧统计异常。

### DeviceFarmer / STF

更早的一代：`minicap`（原生截屏推 JPEG 流）+ `minitouch`（直接写 `/dev/input` 注入触控）。
minitouch 的输入延迟在毫秒级。代价是要为每个 ABI 与 SDK 版本准备预编译二进制。

## 4. 可以借鉴的，按性价比排序

| # | 借鉴点 | 成本 | 收益 | 状态 |
|---|---|---|---|---|
| 1 | **只在画面变化时出帧** | 半天 | 静止时省掉几乎全部节点 CPU 与带宽 | ✅ 已做 |
| 2 | **输入与抓图分离，不互相阻塞** | 半天 | 输入最慢 1.7 s → 0.32 s | ✅ 已做 |
| 3 | **H.264 + WebCodecs 取代逐帧 PNG** | 2~3 天 | 3 → 10 fps，点击反馈进入 300 ms 量级 | ⬜ 未做，见 §5 |
| 4 | **持久控制通道注入输入** | 含在 3 里 | 输入 120 ms → 10 ms 量级 | ⬜ 未做 |
| 5 | 多点触控、剪贴板双向、拖拽推文件 | 各半天 | 便利性，非阻塞项 | ⬜ 未做 |

## 5. 三个选项

### A. 维持现状，只做小优化

再挤也就是把 1.1 s 压到 0.8 s 左右（比如输入后立刻强制抓一帧）。
**够不着「顺手」的门槛**，人还是会重复点。

适用：如果放大操作只是偶尔用一下（每天几次），不值得投入。

### B. 在 droidpoold 里实现 scrcpy 协议客户端（推荐）

- Go 侧：推 `scrcpy-server.jar` → `adb forward` → 读 12 字节帧头 + H.264 包 → WebSocket 转发。
- 浏览器侧：`WebCodecs` 的 `VideoDecoder` 解码，画到现有 canvas，输入照旧走 canvas 手势。
- 输入改走 scrcpy 的控制 socket，省掉每次 `adb shell` 的 70 ms 固定成本。

**预期：10 fps，点击反馈 200~300 ms。** 工作量约 2~3 天。
好处是不引入 Node 依赖，租约与鉴权逻辑仍在一处；`scrcpy-server.jar` 直接取自 scrcpy 发行包。

### C. 旁挂 ws-scrcpy 容器

路线图原本就是这么写的（Phase 3「控制档」），我实现时自己造了 screencap 方案，
现在数据证明那个选择在放大操作场景是错的。

- 成本：半天（docker run + 设备墙上放个跳转链接）。
- 代价：多一个 Node 服务；它自带设备列表 UI，与我们的租约模型是两套；
  跳过去之后看不到 worktree、分支、租约这些上下文。

## 6. 建议

**缩略图墙保持现状**（screencap + JPEG）。墙面只要看清「这台在哪一页」，
0.5 fps 足够，帧去重之后成本已经很低，H.264 在这里是杀鸡用牛刀。

**放大操作视图换成 B（scrcpy 协议 + WebCodecs）**。这是唯一能把点击反馈
拉进人类可接受区间的路径，且不引入 Node 栈、不割裂租约上下文。

如果暂时不想投 2~3 天，就先用 C 顶着，把 B 排进 Phase 3 的后半段。

## 7. 一个仍然存在的天花板

即使换到 scrcpy，**10 fps 也是这台设备的极限**，因为 redroid 用软件渲染、
无硬件编码器。要再往上只有两条路：

- **专项 B：GPU host 模式**（宿主已有补丁版 panfrost，`/dev/dri` 齐备，尚未验证）。
  跑通的话渲染与编码都会显著加速。
- 换 x86 节点用官方模拟器（有 GPU 加速与硬件编码路径）。

这两条都属于 Phase 4，不在当前决策范围内。

## 8. 复现

```bash
# 本项目帧率
curl -s -N "http://<控制面>/api/devices/<id>/stream.mjpg" -o /tmp/s.bin &
sleep 8; kill %1; grep -a -c droidpoolframe /tmp/s.bin   # 帧数 / 8 = fps

# scrcpy 对照
scrcpy -s <ip:port> --no-window --no-audio --record=/tmp/sc.mp4 --time-limit=8
ffprobe -v error -select_streams v:0 -show_entries stream=avg_frame_rate,nb_frames /tmp/sc.mp4

# 点击到画面变化（浏览器控制台，采样整屏像素和直到变化）
# 见本文 §1，脚本在会话记录里
```
